# Existing Work recovery and evidence compatibility

[中文](RECOVERY.zh-CN.md)

A recovery proposal reads current instructions, the existing draft, recorded candidates and real verification history. It does not reopen implementation, issue authority, publish, merge, or reinterpret a paused conflict repair as a requirement to update from main.

Request a proposal for a paused Work with `work.plan_recovery(instruction, request_id=...)` through the Python Service API, or `service ... work plan-recovery WORK_ID --instruction ...`. The returned `job_id` identifies the ordinary durable reasoning job. The result is retained as `recovery_plan` on the same Work. The job uses the configured Lead profile and read-only code/evidence tools. Revised instructions, cancellation or a superseding request invalidate its applicability. Completing the proposal leaves the Work paused.

Owner budget migration is distinct from recovery planning. `RunHandle.configure_budgets` changes selected progress settings only after complete cleanup of a paused/blocked Run. It preserves counters, old grants, source, history and the recorded deadline; a new execution window still needs its normal authorized retry. For an offline Service owner, `ServiceStore.configure_stopped_budgets` validates limited budget/delegation groups, requires a stopped Service, and can synchronize selected settings into the same paused Work and Run. It never edits permission paths, project identity, credentials, code or acceptance. Both operations keep request receipts and reject conflicting reuse of an ID. Refresh the Service binding and start normally after configuration changes.

Legacy Run authorization hashes the originally accepted persisted spec, including when current parsers supply additional default fields. Actual changes to that accepted spec still invalidate old scopes.

Test authorization and evidence remain separate. Current grants bind the current recipe fingerprint. A historical passing receipt from the legacy implicit output limit may apply to the current relaxed output contract only when `hard_output_bytes=null` and every other input, command, environment, resource, role, isolation and test-selection basis matches. A newer related failure prevents reuse. Reuse exposes the original execution time and a compatibility proof; it does not create a new pass or grant. Changing source or imposing a different explicit hard output limit requires applicable verification.

Owned native test receipts are collected into configurable pages (`evidence_page_rows`, default 100). The aggregate retains all page references and completeness; a page size is not a total receipt ceiling. Full legacy inline evidence remains readable. Missing or foreign pages cannot masquerade as complete evidence. Quality queries select the current input/contract and preserve relevant newer failures without loading unrelated histories into model context.

Platform requests have configurable connection/read/write/pool and whole-request windows. Defaults are 30/60/60/30 and 120 seconds. Only GET/HEAD connection failures receive bounded local retries (`platform_read_attempts=3`). An uncertain write is never automatically repeated. Cancellation is observed during active I/O, and diagnostics identify the timeout phase and selected window. Repository polling inherits the declared `request_seconds`; changing polling budgets preserves source cursor identity. Legacy cursor bindings are accepted only for the same bound project and connection.

Publisher account verification is deferred from control-plane construction to source processing or external use. The control API can start during a platform outage. External communication still requires a successful authenticated identity query, and credential identity participates in the binding. Poll failures are observations with retry backoff by default; `communication_poll_attempts` explicitly opts into a hard attempt budget, and reopening starts a new series. No successful remote fact is manufactured to improve readiness.
