# 同一 Work 的恢复与证据兼容

[English](RECOVERY.md)

恢复方案由配置的 Lead 使用只读工具形成，依据最新执行说明、现有草稿、既有候选及真实测试／审查历史。提出方案不会解除暂停、重新开发、授权、发布或合并，也不能把旧冲突修复计划当成必须追随 main 的要求。

Python Service API 支持 `work.plan_recovery(instruction, request_id=...)`；CLI 支持 `service ... work plan-recovery WORK_ID --instruction ...`。返回的 job_id 对应普通持久化研判 job，结果保留在同一 Work 的 recovery_plan。改变指令、取消或更新恢复请求会使旧方案失效。方案完成后 Work 仍暂停。

预算迁移与方案分开。RunHandle.configure_budgets 只允许在 Run 暂停／阻挡且清理完成后调整已列明的进度设置，不重置计数、授权、源码、历史或期限；新的执行窗口仍走正常授权 retry。停机时的 ServiceStore.configure_stopped_budgets 校验预算／明确审批委托组，并可同步同一暂停 Work／Run 的指定设置，不改路径、项目、凭据、源码和验收要求。操作有请求回执，拒绝同一 ID 的不同内容。修改后刷新服务绑定并正常启动。

旧 Run 测试授权继续绑定原始接受的持久化规格；解析器新增默认字段不会让同一规格产生互相矛盾的摘要。真正修改规格仍会使旧作用域失效。

测试授权与验收证据分开：新授权使用当前指纹。只有 hard_output_bytes=null 且其他输入、命令、环境、资源、角色、隔离与测试选择完全匹配时，旧隐式输出限制下的实际通过回执才能兼容当前更宽松合同。更新的相关失败阻止复用。复用保留原执行时间、真实回执及兼容证明，不产生假新通过或新授权。源码或明确输出限制改变时仍需适用验证。

原生回执按 evidence_page_rows（默认100）分页保存，聚合记录所有页及完整性。100是单页窗口，不是总回执上限。旧内联回执仍可读，缺页或跨 Work 页不能伪称完整。质量查询按当前输入／合同选择证据，保留更新失败，不把无关历史全部发送给模型。

平台连接／读取／写入／连接池与整体请求窗口均可配置，默认30／60／60／30秒和120秒。仅GET／HEAD连接失败做有限本地恢复（platform_read_attempts=3），不重复不确定写入。活动请求可响应取消，错误指出阶段及实际窗口。仓库收件使用声明的 request_seconds，调整轮询预算不会改变来源身份；旧游标兼容限于相同项目和连接。

发布者账号核验从控制面初始化延后到收件处理或外部使用，平台暂时不可用时控制 API 仍可启动。外部沟通仍须成功认证核验，凭据身份参与绑定。默认轮询失败是带退避的观察；明确 communication_poll_attempts 才执行次数预算，重新打开会启动新一轮。不会为就绪状态伪造远端成功事实。
