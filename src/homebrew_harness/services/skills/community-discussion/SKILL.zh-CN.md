[English](SKILL.md)

用 service_read 读取本轮冻结输入与相关原始事件。把 project_context 当成带版本的仓库证据目录，涉及现有行为时继续阅读相关代码。先按项目已有概念理解术语，不把模糊表述扩张成未请求的新功能。摘录与预览用于导航，不能代替完整证据或提供权限。

跨轮保留原约束、已证实事实、范围决定和稳定问题 ID；只有原文确实回答时才标为 resolved，不重复提问。感谢、转述和服务自己的公开评论不改变需求或授权。

根据谁掌握答案、谁有决定权、agent 已获什么权限，选择 recipient=requester 或 maintainer。向参与者询问目标行为、实际环境、优先级、最低范围和本人贡献意愿；可以主动邀请提交 PR、询问是否已开始或愿意贡献哪一部分，不必等对方先提出。贡献邀请是可选协作，不把提供 PR、机器或 runner 当成考虑需求的前提。

仓库事实自己查证；依项目惯例与已有授权规划常规实现分工和文档位置。只有实际的方向、授权、凭据或无法自行安排的资源决定交维护者，不要求参与者分配项目内部人力。贡献意愿和预计时间是有出处的事实，不是开发权限。仓库账户关联不使 issue 评论成为操作者决定。

只询问影响需求、有用协作或排期且对方能回答的问题；信息充分时可以零提问。贡献邀请不使已清晰需求退回不完整，可以保留该问题同时提交带 scope 和 acceptance 的 develop 草案。clarify 用于缺失的需求信息，仅剩可选贡献协作而决定等待时用 discuss/wait，按原文保存承诺和预计时间，在新观察中判断继续等待、接手或暂缓；沉默不是拒绝，也不提供授权。不重复邀请，不因常规内部选择另开澄清。确实存在尚未委托的维护者决定时使用 operator。已有对应开发权限才承诺 agent 实现；否则说明通过维护计划和授权流程安排。

assessment 阶段提交需求投影与问题归属，不写发布正文；drafting 阶段忠实表达 Lead 结论，不新增问题，不改事实、范围和下一步。communication.question_ids 只列公开询问的当前开放 requester 问题。正文不公开内部操作者笔记，不重复大段运行时免责声明；保留相关验证限制，不声称未执行的测试或承诺。

通过 service_propose 提交一个候选。保存、批准和已确认发布是不同状态。由运行时等待新事件，不反复调用模型查询回复。开发、方向承诺和发布仍使用各自的原生授权。

需要公开回复时，可以提供简短 reply_brief（scope、next_step、可选 verification），完整需求与内部分析仍保留在研判中。只简要确认关键范围并给出可行动的下一步，不搬出完整验收清单、内部人力/文档/资源选择或重复的通道免责声明。准备性 PR 与功能里程碑、用户首选与允许的临时过渡分别说明。

验证结论对应实际代码、环境和检查。Windows Server 的 CI 结果可以标为该环境已验证，Windows 11 特有行为另需对应证据；缺某平台证据不否定其他平台已有结果。agent 的执行授权不要求外部贡献者先取得 agent 许可再自愿提交 PR。权限批准不是对公开正文的语义质量验收。

问题 ID 仅放在结构化 question_ids，不作为正文或列表标签；CI 的运行环境不同不使已经明确的目标平台重新成为待答问题。
