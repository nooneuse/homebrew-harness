[English](SKILL.md)

用 service_read 读取本轮冻结输入与相关原始事件。把 project_context 当成带版本的仓库证据目录，涉及现有行为时继续阅读相关代码。先按项目已有概念理解术语，不把模糊表述扩张成未请求的新功能。摘录与预览用于导航，不能代替完整证据或提供权限。

跨轮保留原约束、已证实事实、范围决定和稳定问题 ID；只有原文确实回答时才标为 resolved，不重复提问。感谢、转述和服务自己的公开评论不改变需求或授权。

根据谁掌握答案、谁有决定权、agent 已获什么权限，选择 recipient=requester 或 maintainer。向参与者询问目标行为、实际环境、优先级、最低范围和本人贡献意愿；可以主动邀请提交 PR、询问是否已开始或愿意贡献哪一部分，不必等对方先提出。贡献邀请是可选协作，不把提供 PR、机器或 runner 当成考虑需求的前提。

仓库事实自己查证；依项目惯例与已有授权规划常规实现分工和文档位置。只有实际的方向、授权、凭据或无法自行安排的资源决定交维护者，不要求参与者分配项目内部人力。贡献意愿和预计时间是有出处的事实，不是开发权限。仓库账户关联不使 issue 评论成为操作者决定。

只询问影响需求、有用协作或排期且对方能回答的问题；信息充分时可以零提问。贡献邀请不使已清晰需求退回不完整，可以保留该问题同时提交带 scope 和 acceptance 的 develop 草案。clarify 用于缺失的需求信息，仅剩可选贡献协作而决定等待时用 discuss/wait，按原文保存承诺和预计时间，在新观察中判断继续等待、接手或暂缓；沉默不是拒绝，也不提供授权。不重复邀请，不因常规内部选择另开澄清。确实存在尚未委托的维护者决定时使用 operator。已有对应开发权限才承诺 agent 实现；否则用日常语言说明实际公开进度，提出候选不表示已安排开发。

assessment 阶段提交需求投影与问题归属，不写发布正文；drafting 阶段忠实表达 Lead 结论，不新增问题，不改事实、范围和下一步。communication.question_ids 只列公开询问的当前开放 requester 问题。正文不公开内部操作者笔记，不重复大段运行时免责声明；保留相关验证限制，不声称未执行的测试或承诺。

通过 service_propose 提交一个候选。保存、批准和已确认发布是不同状态。由运行时等待新事件，不反复调用模型查询回复。开发、方向承诺和发布仍使用各自的原生授权。

按读者区分现有字段。draft.text 是维护者确认需求时使用的工作说明，完整验收条件和排除项另行保留。reply_brief 是给参与者看的简短提要，scope 通常用一两句话选择关键范围，next_step 通常用一句话表达实际进度与下一步。参与者问题和贡献邀请只放在 questions/public_questions 中，避免在提要中重复。起草保留这些含义并选择简洁表达。提出 develop 候选时表达“这个方向值得跟进”；正式接受、排期或交付表述由真实 Work 状态支持。保留准备性工作与可用功能、首选配置与临时过渡的区别。

验证结论对应实际代码、环境和检查。一个环境的结果不能验证另一个支持目标；缺少其他环境的证据也不否定已有结果。agent 的执行授权不要求外部贡献者先取得 agent 许可再自愿提交 PR。权限批准不是对公开正文的语义质量验收。

问题 ID 仅放在结构化 question_ids，不作为正文或列表标签；CI 的运行环境不同不使已经明确的目标平台重新成为待答问题。

确认需求时，概括用户希望完成的工作流和相对原请求的实质差异；未变化的能力清单保留在完整工作草案中。只有调整、争议或额外提出的范围需要列举。源码查证后表达结论的影响，不搬出完整读取记录。目标已明确时，贡献邀请直接询问是否愿意在该目标上验证；其他环境信息仅在实际协作需要时询问。

work_status 是宿主状态观察；提出 develop 候选不表示已安排开发。使用简短日常表达说明实际进度，内部候选与授权流程保留在维护者研判中。
